**تاريخ:** 2026-10-10  
**المرجع:** docs/audit/2026-10-10_INDEPENDENT_DEFECT_REGISTER.md  
**قاعدة الفحص:** تقييم السبب قبل التعديل، لا تعديل/نشر هنا. كل اقتراح في هذا الملف يحتاج قياسًا واختبارًا وقرارًا مستقلاً؛ لا نستبدل الترقيع بإعادة كتابة عمياء.

## 1. الجذر RC-01 — قواعد CSS متعددة تعالج العنصر ذاته من اتجاهات مختلفة

**المشاهدة (مؤكد من المصدر):** scripts/build.mjs يجمع src/styles/home.css وservices.css وservice-detail.css وcontact-planner.css ثم يلحقها بـ hero-home.css وhero-pages.css وhero-responsive.css وtext-flow.css. المثال الواضح: وصف Hero في service-detail.css ثم clamp/line-clamp في hero-pages.css ثم font قياسي عام في text-flow.css. زر Hero موجود في القالب ثم يُخفى في نهاية hero-responsive.css بواسطة display:none لكل المقاسات.

**التأثير:** أصعب معرفة من يملك تعريف الهيرو؛ تعديل محلي قد يختفي بسبب override لاحق؛ احتمالات اختلاف breakpoint 768/1024 والقراءة والتنقل.

**غير مقبول كحل:** إضافة !important أو قاعدة CSS أخيرة أو إخفاء المزيد من الأزرار أو اجتزاء النص تلقائيًا حتى يتناسب مع القالب.

**المعالجة الجذرية المقترحة:** جرد الـselectors الفعالة وإسناد مسؤولية وحيدة لكل component، تعريف عدد محدود من variants لهيرو صفحات مختلفة، مقاسات خط fluid واضحة، وقف تخصيص عام واسع داخل text-flow.css حيث يمكن استعمال tokens مستقرة. حذف overrides فقط بعد المقارنة البصرية/الوظيفية لكافة القوالب وAR/EN؛ لا حذف عالمي غير محسوب.

**الإغلاق:** لا ازدواج مؤثر في CSS لنفس المكون بلا سبب موثق + صور مقارنة 360/390/768/1024/1440 + keyboard zoom + لا قص.

**المعرفات:** WT-IA-02/08/09/10/14/16/38، WT-009.

## 2. الجذر RC-02 — القوالب لا تستخدم عقود سلوك صحيحة للـCTA

**المشاهدة:** زر باسم «اكتشف خدماتنا» في main يسير إلى startProject وزر «تواصل معنا» إلى portfolio. اختبار check-home.mjs في main يؤكد وجود الخدمات والصور والنصوص، لكنه لا يربط تسمية CTA بوجهة متوقعة؛ من الممكن أن تكون الاختبارات كلها PASS مع تجربة خاطئة.

**غير مقبول كحل:** إصلاح رابطين ثم ترك نمط «اسم الزر منفصل عن href» في باقي الأقسام، أو تغيير التسمية لتبرير وجهة غير مقصودة.

**الجذر:** content.primaryCta مجرد سلسلة نصية، بينما href يحدده كل قالب يدويًا، من دون semantic action type أو route contract.

**الحل الجذري:** action entity موحد مثل intent=explore-services/contact/start-project/view-work؛ mapping ثابت يحدد label وhref بالتطابق وفق locale؛ مع override حقيقي فقط إذا وُثق الاختلاف، واختبار اختيارات CTA المتوقعة لجميع صفحات القوالب. لا نغير محتوى النصوص المدعومة بلا اعتماد.

**الاختبار:** snapshot DOM لكل موقع CTA، سؤال تحويل حقيقي من الرئيسية والخدمات والتواصل، وعدم وجود labels تزعم فعلًا آخر. PR45 يعالج الرئيسية فقط (لا يغلق التقييم الشامل).

**المعرفات:** WT-006، WT-IA-01/21/27.

## 3. الجذر RC-03 — نموذج «راجع التفاصيل» له مسار فشل قد يكشف معلومات

**المصدر:** src/pages/project-planner.js يحتوي form + inputs (name, phone, details)، دون method أو action ويستخدم novalidate؛ src/client/project-planner.js هو الذي يمنع الإرسال الافتراضي بـ preventDefault. إذا فشل تحميل JavaScript أو عطل المستخدم تشغيله، يتبقى زر submit HTML الافتراضي؛ المتصفح يختار GET إلى الصفحة نفسها ويضيف محتوى الحقول إلى URL. وعلى شاشة المراجعة لا يوجد في النظام نفسه حدث «تم إرسال الطلب»؛ الانتقال إلى WhatsApp اختياري منفصل.

**التأثير:** بيانات أدخلها الزائر قد تظهر في عنوان المتصفح/السجل/طلبات الشبكة في سيناريو غياب JS. ليست لدينا أدلة على حدوث تسريب فعلي لأحد، لكن مسار الشيفرة يستلزم المعالجة الوقائية قبل إعلان خصوصية النموذج.

**لماذا «ترقيع»؟** الحل JS-only يتعامل مع المسار السعيد، واختبار check-contact-planner.mjs يمنع POST/action صراحةً من باب عدم الادعاء بوجود backend، لكنه لا يفحص GET الافتراضي عند غياب JS.

**المعالجة الجذرية:** تحديد عقد واضح: النموذج client-side-only، لا يفترض إرسالًا للخادم. عند تعطيل JS لا يسمح إرسال حقول بآلية GET، بل يقدم طريق تواصل واضحًا وآمنًا. إن اعتمد لاحقًا backend: POST مصادق + rate limiting + سياسة بيانات، لا استعمال URL GET. توثيق الرسالة للزائر بدقة «لم نرسل المعلومات بعد».

**اختبار مانع إطلاق:** تعطيل JS في AR/EN وتحميل الصفحة مباشرة، تعبئة قيم اختبار غير حقيقية فقط، محاولة submit؛ URL لا يحتوي name/phone/details ولا طلب GET به. ثم JS enabled يتأكد review→WhatsApp ويعرض الرسالة الصحيحة؛ لا حقول اختبار حقيقية في logs.

**المعرفات:** WT-IA-18/36/37، WT-008/019.

## 4. الجذر RC-04 — التصميم يعتمد على أعداد ثابتة غير متوافقة مع البيانات

**المصدر:** src/pages/home.js يكوّن 4 processSteps، بينما src/styles/home.css يعلن home-process__steps شبكة 3 أعمدة للكمبيوتر. Screenshot from CI home-ar-desktop-1440.png يُظهر الثلاثة أولى في صف، والرابعة منعزلة تحته. أيضاً شبكة Why تستخدم auto-fit minmax وتُظهر 5 ميزات في صف وواحدة وحيدة تحته عند 1440.

**غير مقبول كحل:** إخفاء الخطوة الرابعة، زيادة margin عشوائي، أو تعديل width خاص لتصحيح لقطة واحدة.

**الحل الجذري:** component grid مبني على نوع وعدد المحتوى، 4 steps = 4 equal columns عند العرض الكافي، 2x2 عند التابلت، 1x4 عند الهاتف؛ و6 features = 3x2 أو 2x3 بتوزيع مضبوط. التطابق AR/EN والعناوين الطويلة شرط قبول.

**دليل الصورة:** GitHub Actions Run 38073282131، Artifact 11677911173. لا يجوز نسبة هذه الصورة إلى الموقع الحي قبل نشر PR45.

**المعرفات:** WT-IA-07/39/40.

## 5. الجذر RC-05 — أنماط fallback تضيف إصلاحًا شكليًا دون حل سلوك HTTP الأساسي

**المثال:** src/pages/not-found.js على integration يستخدم وثيقة عربية عامة ورسالة إنجليزية client-side عندما يبدأ pathname بـ /en/. الصياغة تحاول الحفاظ على رمز HTTP 404 مع تحويل النص. لا تختبر حقيقة إعادة النطاق/status عند unknown route على Vercel، أو ماذا يرى المستخدم إذا عطل JS.

**إيجابي:** صفحة 404 في Preview الآن مستقلة بالفعل بالصورة والنص والزر والـRTL/LTR، وحزمة الصور CI متاحة. لا نعيد تصميمها لمجرد وجود workaround؛ نثبت أين ينجح وأين يفشل.

**الجذر:** build-static لا يتملك HTML/locale لأي مسار غير موجود. يجب أن يتوافق server routing مع اختيار اللغة وحالة HTTP.

**الحل:** اختبار /nonexistent/, /en/nonexistent/ مباشرة على deployed Preview/Production لـstatus=404 وlang/dir/home action. إن كانت الاستجابة الإنجليزية تعتمد على JS فقط، تحديد تصميم fallback server-side يتوافق مع المنصة، أو الاحتفاظ بها كقيد موثق إذا كان تعقيد الخادم أكبر من قيمته مع no-JS fallback مفهوم. ممنوع تحويل 404 إلى 200 بالإعادة للرئيسية.

**المعرفات:** WT-007/019، WT-IA-04/41.

## 6. الجذر RC-06 — «CI أخضر» لا يساوي دليل صحة الوظيفة والمحتوى

**المصدر:** check-home.mjs يراجع وجود كلمات وصور وتتابع أقسام، لكنه لم يكشف CTA الخاطئة. check-services.mjs يتأكد أن البطاقات والثماني خدمات موجودة، لا أن كل وصف يطابق عنوانه. check-contact-planner.mjs يمنع backend افتراضي لكنه لم يحمِ GET no-JS. capture-vnext-route-matrix.yml يراجع بعض عائلات القوالب وعينة من المشاريع والخدمات والمقالات.

**الإيجابي الموثق:** PR45 لديه ثلاث مهام GitHub Actions ناجحة على SHA 971c7d31 تشمل VNext verify/media/route matrix؛ تمت قراءة 72 screenshot من Artifact run #38073282131.

**الحل الجذري:** فصل 4 بوابات مستقلة: (1) syntax/build + assets، (2) contracts الدلالية والخصوصية، (3) keyboard/UX/E2E والرؤوس الحقيقية، (4) بشرية بصريّة مع screenshots before/after. إضافة اختبارات فشل أولًا قبل كل fix P0/P1، ثم إثبات فشل الاختبار على main ونجاحه على branch (إن أمكن محليًا/CI). إبقاء اختبارات visual as artifact لا يعني حكم قبول تلقائي.

**المعرفات:** WT-013/019، WT-IA-03/27/37/43/44/46.

## 7. الجذر RC-07 — خلطة Code/Preview/Production/Docs تولد إعلانات إنجاز خاطئة

**المصدر:** سجل WT بتاريخ 10 أكتوبر يقول إن النطاقات غير مرتبطة وبقيت 2/8 صور؛ لكن استعلام Vercel الحالي يعرض كلا النطاقين Verified، ومقارنة PR45 تضم 8/8 WebP + 8/8 PNG ونجاح CI. في المقابل لا تزال كل تلك الإصلاحات خارج main وProduction.

**الجذر:** الوثائق تعكس لحظة، والعمل ينتقل بين فروع، لكن status لا يرتبط بـbranch+SHA+channel.

**الحل الجذري:** لكل مشكلة حقول مستقلة: Source baseline SHA؛ Fixed on branch?؛ Merged into main?؛ Built?؛ preview screenshot accepted?؛ live production verified?؛ إذا اختلفت SHA/branch لا نستخدم CLOSED. تُجمع الملاحظات المتداخلة تحت ID واحد/روابط موجودة؛ تحديث حي من GitHub/Vercel قبل تغيير الوضع.

**المعرفات:** WT-001..020، WT-IA-05/22/23/30/46.

## 8. الجذر RC-08 — المحتوى والهيكل يخبران عن قدرات أكثر مما يثبتانها

**المصدر:** في src/data/services.js خدمة تطوير المواقع تحتوي deliverables بعناوين وأوصاف غير مطابقة؛ عند src/pages/service-detail.js renderProof يعرض صور أعمال بلا href؛ ودراسات حالة project-detail.js تعرض وصفًا عامًا وصورة رئيسية واحدة.

**غير مقبول:** مجرد تنميق النصوص، أو ملء المشاريع بصور Mockup لا تمثل تنفيذًا حقيقيًا، أو إخفاء الأقسام الضعيفة بالـCSS.

**الجذر:** لا توجد طبقة تحقق تحريرية تربط الحقول بعقودها الدلالية ولا Evidence للقصة/المشروع، واختبارات الخدمات تحقق وجود العناصر لا معناها.

**الحل:** Review spreadsheet/structured checklist عنوان→وصف→مخرج→دليل→ترجمة، تدقيق 8 خدمات/المقالات/الأعمال قبل النشر. روابط دراسات الحالة إن وجدت، وأدلة حقيقية بإذن صاحب العمل. تختار جودة المحتوى على كثرة الأقسام.

**المعرفات:** WT-IA-03/11/12/19/20.

## 9. ملاحظات لا تعتبر Bugs دون دليل

- Dark theme: src/styles/brand.css يشمل capability ولا يعرض toggle؛ لا نحكم بفقد ميزة إلزامية دون قرار منتج.
- حمل Google Fonts وsingle CSS: قياس LCP/CLS/waterfall قبل إعادة هندسة؛ وجودها ليس وحده فشل أداء.
- وثيقة headers في vercel.json لا تثبت غياب headers على كل Response؛ افحص فعلية HTTP أولًا.
- صور hero alt فارغ قد يكون صحيحًا للصور الزخرفية؛ قرار حسب معنى الصورة وليس كل الصور.
- إخفاء أزرار Hero قد يكون اختيارًا تصميميًا مقصودًا؛ يجب تقييم أثره عمليًا وعدم تسميته bug حتميًا دون سلوك conversion ثابت.
- فحص موضع النصوص والقص يحتاج live screenshots في Production بعد الإصدار، لا يكفي Preview CI.

## 10. قالب منع الترقيع لأي إصلاح جديد

1. المعرف + وصف أثر المستخدم + أين يمكن إعادة الإنتاج ونسخته.
2. تصنيف مؤكد/اشتباه + دليل وصورة/اختبار وقيمة فعلية.
3. حدّد المالك الحقيقي للعلة: data، template، component، CSS، client JS، server config، content، release.
4. لماذا ظهرت؟ ولماذا لم يلتقطها الاختبار؟ وهل أصلحنا symptom فقط؟
5. الحل الأقل تعقيدًا الذي يزيل الجذر ويمنع التكرار؛ بدائل ومخاطر.
6. اكتب test فاشلًا بالمشكلة أولًا إن كان عمليًا، نفذ التغيير، أعد تشغيل كل gate ذي صلة.
7. وثّق Before/After في AR/EN والجوال والديسكتوب، وسجّل branch+commit/CI وProduction منفصلين.
8. أزل workaround السابق إذا صار غير ضروري بعد التحقق؛ لا تترك workaround فوق patch جديد.
9. لا يساوي إنشاء PR أو READY أو Commit إغلاق المشكلة بمفرده.

## 11. حدود هذه الدفعة

استطعت استرجاع 72 screenshot حقيقية من CI وأراجع بصريًا أمثلة رئيسية، لكن محاولة تشغيل Playwright محليًا ضد خادم 127.0.0.1 في الحاوية مُنعت بالسياسة net::ERR_BLOCKED_BY_ADMINISTRATOR. لذلك **لم أصف أي رحلة محلية بهذه المحاولة بأنها PASS**، ومسار no-JS مصنف CODE-CONFIRMED من دلالات نموذج HTML ويحتاج browser regression رسمي. كذلك لم تُنفذ أي كتابة على main أو نشر.
