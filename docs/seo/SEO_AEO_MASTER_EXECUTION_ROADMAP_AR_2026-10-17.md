## 2) الهدف والحدود

**الهدف:** جعل صفحات وصل تك مفهومة وقابلة للاكتشاف وقوية عند البحث عن خدمات فعلية في اليمن والخليج؛ كل صفحة تجيب عن نية محددة وتُظهر ما يثبت التنفيذ. رفع فرص الاستشهاد في نظم الإجابة والبحث بالذكاء الاصطناعي **دون وعد بظهور أو ترتيب مضمون**.

**يشمل:** Technical SEO، الفهرسة والزحف، On-page، بنية المحتوى والتفرد، هوية العلامة، دراسات الحالة، المقالات، الصور والأداء، البيانات المنظمة، الروابط الداخلية، Bing/IndexNow، GSC/GA4، AEO/GEO، QA ثنائي اللغة.

**لا يشمل:** منشورات التسويق والسوشيال وخطة نشرها، إعادة تصميم الموقع بلا سبب مثبت، شراء الروابط/التقييمات، اختلاق إنجازات العملاء، إنشاء محتوى بالجملة، تغيير العلامة، تكرار كلمات مفتاحية مخفي، توليد عشرات صفحات المدن دون خدمات ومحتوى محلي حقيقي.

## المرحلة 01 — حل التحويلات جذريًا

**المشاكل:** `/index.html`، `/en/index.html` يعيدان 200 بدل تحويل دائم؛ روابط `service-web?id=...` قد تنتهي إلى دليل الخدمات بدل الخدمة المطلوبة؛ إشارات `www` و`.html` و`http` القديمة في GSC.

**الخطوات:**
1. استخرج جميع الروابط القديمة من GSC (Pages / query-page)، Bing، المستودع وقواعد Vercel الحالية، وأنشئ جدول source→expected destination. لا تقتصر على الأمثلة الأربعة.
2. افحص `GET` و`HEAD` مع تتبع **كل hop وLocation** للمضيفين HTTP/HTTPS وwww/apex، وتأكد من وجود 301/308 دائم وليس 200 أو soft 404؛ اختبر شرطات النهاية والتطابق الجزئي.
3. راجع `vercel.json` وVercel project-level redirects وتداخل `routes` مع `redirects`؛ تجنب تعارض `handle: filesystem` وقواعد 404.
4. ضع تحويلًا دائمًا `/index.html → /` و`/en/index.html → /en/`؛ حافظ على canonical واحد لكل لغة دون أن يمنع عرض صفحات HTML الأساسية.
5. ارسم **خريطة معرفات الخدمة القديمة المعروفة** من بيانات الخدمات الرسمية؛ اختبر `/service-web?id=web-development` → `/services/web-development/`، `mobile-app-development` → صفحة التطبيق، وبقية المعرفات المعروفة عندما تُثبت. للأسماء مجهولة/ناقصة/غير صالحة اختَر سلوكًا غير مضلل (404 حقيقي أو دليل مناسب إن كانت النية عامة)، وتجنب تحويل كل ID إلى خدمة عشوائية. أزل query من URL النهائي إن كان مطلوبًا، ولا تمرّر query القديم تلقائيًا دون اختبار.
6. اختبر `/about.html` و`/contact.html` والمسارات القديمة ذات الزيارات أو الروابط؛ وفّر دائمًا أقصر سلسلة عملية `www/http → apex HTTPS` عندما تسمح الإعدادات.
7. أضف اختبارًا آليًا لمصفوفة redirects (status + Location + final path + no loops + language preservation)، ثم تحقق على Preview/Production.

**قبول:** جميع legacy URLs الموثقة لها نتيجة متوقعة؛ لا HTTP 200 لنسخة index.html المكررة؛ لا حلقات/سلسلة خاطئة/تحويل AR إلى EN؛ لا يتعطل sitemap/robots أو المسارات الصحيحة؛ لا اختفاء للرابط القديم قبل تحقق بيانات Google.  
**مراجع تقنية رسمية:** Google canonical/redirect guidance: `https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls`؛ Vercel `redirects` و`has: query`: `https://vercel.com/docs/project-configuration/vercel-json` و`https://vercel.com/kb/guide/how-do-i-perform-vercel-redirects-based-on-query-strings`.

**قبول فني:** لا أخطاء معلومة من جانب الموقع على الأربع؛ الـ88 مطابقة، جميع عناصر الزحف الفنية سليمة، وتوثيق أسباب قرار Google إن توفرت. **قبول فهرسة Google منفصل**؛ لا يُعتمد 88/88 إلا إذا أثبته GSC لاحقًا.

**المطلوب:** توزيع بحث تجاري ومعلوماتي/علامة على صفحات واضحة بدل المنافسة الداخلية.

**الخطوات:**

2. كوّن نوايا البحث حسب اليمن والسعودية والإمارات وأسواق الخليج الأخرى: **خدمة عامة، خدمة فرعية، مقارنة/سؤال، مشروع يشبه المطلوب، بحث باسم العلامة**. الكلمات المحتملة تحتاج إثبات حجم ظهورها أو تمييزها «فرضية» إن لم تتوفر بيانات.
3. عيّن URL أساسيًا لكل نية: **الرئيسية** للعلامة والعرض العام، **دليل الخدمات** للاستكشاف، **صفحة الخدمة** للنية التجارية، **المقال** للنية المعلوماتية، **دراسة الحالة** لإثبات عمل مشابه.
4. افحص التداخل بين `web-development` و`ecommerce`، و`custom-software` و`technical-solutions`، و`brand-design` و`company-profiles`، والصفحات العامة/المقالات/المشاريع؛ استخدم تحليل Cannibalization كإشارة لا كدليل نهائي.
5. راجع كل `title`, `meta description`, H1 ومقدمة الصفحة والـOG بنفس النية؛ أي تغيير يُبرَّر بفجوة فعلية. لا تشترط طول 60/160 حرفًا حرفيًا، ولا تستخدم `meta keywords` أو حشو «اليمن والخليج».
6. اعمل مقارنة محايدة مع أفضل صفحات نتائج البحث **للكلمة والبلد والجهاز** عند الإتاحة، وسجّل فجوة الإجابة/الثقة/الدليل، وليس تقليد المنافسين.
7. أنشئ سجل `keyword / locale / country / intent / primary URL / supporting pages / impression/click/position / evidence / edit / status`.

**قبول:** 8 خدمات ذات نية متمايزة، 16 مشروعًا ذات نوع عمل معلوم، 8 مقالات لا تنافس نسخ الخدمات على نفس النية، وربط طبيعي بين الطبقات؛ مراجعة عملية لجميع الـ88 دون إعادة كتابة لغير سبب.

3. فحص من نحن، التواصل، ابدأ مشروعك، طريقة العمل، FAQ، الأدلة، سياق تواصل العلامة، والعناوين المكتوبة «وصل تك/وصلتك» بدون تكرار غير طبيعي؛ إثبات أي حاجة لتحسين.

## المرحلة 10 — قياس الأداء وMedia/CDN

1. التقط PageSpeed Insights/CrUX إن توفرت لكل نمط: الرئيسية، دليل خدمات، تفاصيل خدمة، مشروع، مقال، Contact على Mobile/Desktop. اجمع `LCP`, `INP`, `CLS`, TTFB عند توفر العينة، مع 75th percentile للبيانات الميدانية إن توفرت؛ سجّل مصدر القياس وتاريخه. لا تخلط Lab مع Field.
2. افتح Network waterfall، حدد الصورة الرئيسية الفعلية والخطوط والـCSS والـJS والموارد الخارجية؛ جرّب اتصالًا بطيئًا ونشاطًا نموذجيًا على الهاتف.
3. راجع `AVIF/WebP`, `srcset/sizes`, الأبعاد، `loading` و`fetchpriority`، ومخاطر تخطي حد تحميل الصورة/الحروف. لا تضغط الصورة إلى حد يتلف وضوح المشروع.
4. قيّم `Cache-Control` على HTML/الصور و`x-vercel-cache` والـETag. **`max-age=0,must-revalidate` ليس خطأً مثبتًا وحده**؛ إن ثبت أثر على زمن التحميل أو نقل البيانات، استخدم استراتيجية assets ذات أسماء إصدارات وعمر Cache طويل عند ضمان invalidation الصحيح. لا تجعل HTML لا يتحدث بعد النشر.
5. حل المشكلات المثبتة حسب شدة التأثير وأولوية الصفحة، ثم أعد قياس نفس السيناريو ولا تنقل تحسينًا من موقع آخر دون حاجة.

**قبول:** baseline وafter لكل إصلاح، استقرار visual/mobile، لا CLS أو أخطاء عرض جديدة، عدم كسر التحديث الفوري للصور/الأصول عند النشر.

## المرحلة 11 — القياس والبحث متعدد المحركات والمتابعة

1. **GA4/Consent:** راجع `src/client/analytics.js`، التهيئة `analytics_storage: denied` وآلية موافقة المستخدم الفعلية، وحالة إرسال قياسات الزيارة؛ لا تغيّر موافقة المستخدم أو تفعّل تتبعًا غير مصرح دون دراسة الخصوصية ومتطلبات السوق. عرّف أحداث قياس ذات مغزى (نقر واتساب، إرسال نموذج صالح، بدء مشروع) مع عدم تسجيل بيانات حساسة في URL/Analytics.

3. **Bing/IndexNow:** مراجعة Sitemaps وحالة الزحف ومشكلات Bing، واستعمال IndexNow فقط للروابط الجديدة/المحدثة في محركاته المدعومة؛ تحقق من استجابة الإرسال دون تفسيرها كفهرسة مؤكدة.
4. **AI referrals:** تقرير GA4 مستقل للمصادر المعروفة (إذا ظهرت فعليًا) مع جلسات/تفاعل/استفسارات؛ عدم وجود جلسات لا يثبت أن الموقع لم يُذكر داخل أي جواب AI.

6. **المتابعة الدورية:** أسبوعيًا تغيّر الفهرسة والأخطاء والطلبات الجديدة؛ شهريًا مقارنة الكلمات التجارية وغير التجارية وCTR والبلدان والمحتوى وAI referrals. الأعمدة: baseline/date/fix/SHA/GSC settled-through/impact/status/caveat/next action.
7. **قرار التحسين المستمر:** الأولوية للصفحات التي تحصل على ظهور دون نقر أو تعاني نقص نية/دليل مثبت، وليس لمجرد محاولة تغيير العنوان كل أسبوع؛ تجنب إحداث تقلبات متتابعة يصعب قياس أثرها.

**قبول:** تقارير قابلة لإعادة التنفيذ دون الوصول إلى أسرار الحسابات، حالات consent واضحة وملتزمة، الفحوص الحية موثقة، صفر P0، وكل بند P1 إما مُغلق فنيًا أو معلّق مع سببه الخارجي أو مستند إلى دليل مطلوب.
