## ما تم في فرع المرحلة

1. `vercel.json`: قواعد تحويل دائم 308 مرتفعة الأولوية للنسخ القديمة `/index.html`, `/en/index.html`, `/about.html`, `/contact.html`. قواعد `has(query.id)` تُميّز **ثماني خدمات** بلغتين وتقبل slug الأساسي أو id الداخلي، وتوجه إلى الخدمة الصحيحة؛ 36 قاعدة واضحة بدل fallback العام. مجهول الخدمة له fallback 404 ضمن `routes`، لكن فاعليته في Vercel تحتاج تحقق HTTP مستقل.
2. المحافظة على `trailingSlash: true`، خطوط `Cache-Control` والـsecurity headers، والـ404 العربي والإنجليزي.
3. `scripts/check-legacy-redirects.mjs`: تحقّق آلي من 36 قاعدة (8 خدمات × لغتين × صيغتين + 4 HTML)، ومن سلامة المسارات وغياب التكرار/الحلقات، وتطابقها مع مصدر `services` و`routes`.
4. `.github/workflows/vnext-verify.yml`: جعل اختبار التحويلات جزءًا من `VNext verify` وRelease وMedia.
5. تحديث فحوص `check-source-ownership.mjs` و`check-secondary-legal.mjs` لدعم قواعد التحويل قبل مرحلة filesystem مع **الحفاظ على فحص رؤوس الأمان وترتيب مسارات 404**؛ لم تُحذف اختبارات الحماية.

## الفحوص والقيود (أمانة التوثيق)

- اختبارات GitHub VNext للـSHA `e74f36e837aecd3b45f2fcbe61548aa0af407d23` **SUCCESS** في run `38991634291`، بما في ذلك التحقق البنيوي من `vercel.json` و36 redirect وBuild/Release/Media.
- تجربة **Preview HTTP السابقة قبل التحويل إلى قواعد `redirects` عالية الأولوية** أظهرت أن بعض قواعد `routes` لم تحقق الوجهة الصحيحة وأن `/en/index.html` ظل 200؛ لذلك تم تعديل التنفيذ إلى `redirects` وشرط query exact بدلاً من التوقف عند نجاح اختبار ساكن.
- **حتى تحرير هذا المستند لم يظهر نشر Vercel Preview جديد يطابق SHA `e74f36...`.** أحدث معاينة `READY` المعروضة كانت SHA `3113d697...` الخاص بالإصدار السابق، وليست مرجعًا لإعلان نجاح أحدث تعديل.
- افتراضيًا قد تُمرَّر query string `id` في Location حتى مع اختيار الوجهة الصحيحة؛ يجب اختبار المسار النهائي والـcanonical، ولا يُعلَن حذف البارامتر إلا إذا ثبت.
- قائمة legacy المستخرجة حتى الآن ليست بالضرورة كل روابط الموقع القديمة؛ نحتاج استكمال الجرد من بيانات Google/Bing وتاريخ Git ثم اختبار GET/HEAD وLocation والوجهة النهائية.
- **قرار:** لا دمج لهذا الفرع ولا بدء المرحلة 02 إلا بعد Preview READY بنفس SHA واختبارات HTTP حية تُثبت تحويلات HTML وخدمات الاستعلام وصحة 404 للمجهول، ولا يتم الدمج دون موافقة المستخدم «تم».

## مانع خارجي تم إثباته في Vercel (17 أكتوبر 2026)

أُجريت محاولة إنشاء **معاينة Preview فقط** من SHA `a1d0a0c6355e41fdac2038387dd084f13334c7a5` عبر GitSource المتصل، ولكن Vercel أعاد:

```text
HTTP 402 payment_required
code: api-deployments-free-per-day
Resource is limited - try again in 24 hours (more than 100)

```

هذه **حصة نشر الحساب** وليست مشكلة كود مؤكدة؛ آخر نشر جاهز لنفس الفرع يرجع إلى SHA قديم `3113d697...`، لذلك لا يصح اختبار هذا النشر القديم باعتباره التعديل النهائي. كما أن واجهة Bulk Redirect API أعادت `403 upgrade_required` على خطة الحساب؛ لا ننقل التحويلات إلى خدمة مدفوعة أو نغيّر الخطة تلقائيًا.

**النتيجة:** لا يجوز دمج PR #67 أو إعلان نجاح تحويلات 308 على الإنتاج قبل نجاح معاينة محدثة والتحقق من Location. اختبار GitHub الداخلي للـSHA `e74f36...` نجح لكنه يثبت اتساق **المصدر والقواعد** فقط.

**قرار المعالجة:** يبقى PR Draft. عندما تسمح الحصة بالنشر مجددًا، يعاد تشغيل Preview ثم فحص جميع الروابط. خيار ترقية خطة Vercel قرار للمستخدم وليس شرطًا تقنيًا لتصحيح الكود.

## تحديث التدقيق بدون دمج أو نشر — 17 أكتوبر 2026

**تعليمات المستخدم الحالية:** استكمال العمل في الفروع فقط **دون دمج في `main`، ودون نشر إنتاج أو إنشاء معاينة جديدة**. يتم اختبار الكود آليًا وتُترك بوابة الاختبار الحي مفتوحة إلى حين السماح بها؛ لن نعتبر تحويلات HTTP مثبتة على Vercel لأن الإصدار النهائي لم يُنشر.

### مراجعة جرد الروابط القديمة

- بعد فحص قائمة الملفات المتقاعدة في `scripts/check-source-ownership.mjs`، أُضيفت المسارات القديمة الموجودة بالفعل في تاريخ المشروع:
  `/services.html` → `/services/`، `/portfolio.html` → `/portfolio/`، `/process.html` → `/process/`، `/faq.html` → `/faq/`، `/blog.html` → `/insights/`.
- أضيفت صيغة `/service-web.html?id=...` التاريخية، وصيغتا `/service-web` و`/service-web/`، لكل الخدمات الثماني باللغتين، وبمعرّف الخدمة أو slug الرسمي.
- إجمالي مصفوفة `vercel.json.redirects` الآن **105 تحويلات دائمة**: 9 مسارات HTML أساسية + 8 خدمات × لغتين × صيغتي المعرّف × 3 أنماط URL = 96 تحويلًا.
- شُدد الاختبار `scripts/check-legacy-redirects.mjs` بحيث يشتق الروابط من مصدر الخدمات الرسمي ويتحقق من القواعد وعدم تكرار المصادر وعدم التحويل لوجهة مضللة.
- أضيف `scripts/check-legacy-redirects-live.mjs` للتحقق لاحقًا، قراءة فقط، من HTTP GET/HEAD و308 وLocation والصيغ غير المعروفة، **ولا يعمل دون عنوان معاينة مصرح بها**.
- **GSC:** تحليل search-analytics للبحث عن `wasl tech` أظهر عناوين قديمة حقيقية: `https://www.wasl-tech.com/about.html` و`https://www.wasl-tech.com/contact.html`. لم تُظهر سجلات URL Inspection المخزنة روابط قديمة، فلا نبالغ بالاستنتاج من بياناتها.
- **Bing Crawl Issues:** لا توجد مسائل في الأداة حاليًا، ولا يعتبر ذلك إثباتًا لغياب روابط قديمة غير مكتشفة.
- **ملاحظة رسمية:** إعدادات Vercel `has` في التحويلات تدعم فرز `?id=...`، لكنها **تمرّر query string للمسار النهائي افتراضيًا**؛ لذلك قد تصبح `/services/web-development/?id=web-development` بدل رابط نظيف. يعتمد SEO على canonical الصحيح في الصفحة، لكن إزالة `id` النهائية تبقى قرارًا مشروطًا باختبار Live أو حل مستقل موثّق.

## مراجعة جذور المشكلة وإلغاء خطر الترقيع — 17 أكتوبر 2026

**التقييم:** الإصلاح القديم المبني على إدخال 105 قاعدة متفرقة داخل `vercel.json` كان **معالجة صحيحة للمسارات المستهدفة لكنه ناقص معماريًا**؛ لأنها كانت قائمة يدوية معرضة للتباعد مع `src/data/services.js`، وكان اختبارها يكرر جدولًا شبه مطابق بدل الحصول على التوقع من مصدر وحيد. النجاح في GitHub لا يثبت عمل redirect على شبكة Vercel.

**الإصلاح المعماري في فرع المرحلة 01، دون دمج أو نشر:**
1. `src/seo/legacy-redirects.js`: مصدر وحيد مُوثّق لتسعة مسارات تاريخية وخدمات `services` الحية، وأنماط URL الثلاثة بكل لغة ومُعرّف؛ يولد **105** قواعد من هذه الحقيقة بدل تعديل 105 سجلات يدويًا.
2. `scripts/sync-legacy-redirects.mjs`: `--check` للقراءة فقط و`--write` لتحديث Vercel manifest حتميًا، لأن Vercel يقرأ `vercel.json` **قبل** البناء؛ توليده داخل build وحده لن يعمل.
3. `scripts/check-legacy-redirects.mjs`: فحص الانجراف الفعلي، فرادة المصدر/الشرط، ومطابقة كل وجهة لمجموعة `getIndexableEntries()`، و404 للـID المجهول، والحفاظ على نظام المسارات وحارس الأمان.
4. GitHub Workflow يفحص التزامن والبنية كلما تغير `vercel.json` أو المصدر، ولا يكتفي باختبار أن «هناك 105 قاعدة».
5. `scripts/check-legacy-redirects-live.mjs`: اختبار قبول read-only مُجهز (GET/HEAD و308/Location والوجهات النهائية HTTP 200 وself canonical و404) على **Preview يحمل نفس SHA** عندما يسمح المستخدم/الحصة.
6. فُصل إصلاح المسارات عن توجيه www/HTTP الذي يجب قياسه على إعدادات الدومين في Vercel؛ لا نضيف قواعد مضيف تخمينية قد تُنشئ حلقات.

**إثبات CI النهائي للتعديل المعماري:** `VNext Verify` على SHA `14be575e0fa2445017ca9a9f67edfc86835d7c70` **SUCCESS** في run `38994128741` و`38994125525` (قبل توسيع فحص Live الاختياري). تم تصحيح مقارنة JSON الخاطئة أولًا: اختلاف ترتيب مفاتيح الكائنات ليس اختلاف قواعد؛ المعيار الآن مقارنة دلالية ثابتة مع بقاء ترتيب القواعد حاسمًا. أي commit لاحق يتطلب إعادة قراءة CI لنفس SHA.

**حد الإثبات:** **لم تُختبر نسخة Vercel المنشورة بنفس SHA** لأن المستخدم منع النشر ولأن quota Preview أبلغت سابقًا عن قيد 402. لذلك **TECH-01 إلى TECH-04 غير مغلقة إنتاجيًا** ولا يجوز القول إن الإصلاح «جذري ومؤكد على Vercel» قبل اختبار السلوك الحي. هذا ليس سببًا لإضافة ترقيع جديد بلا دليل.
